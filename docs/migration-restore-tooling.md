## First private inspection when the export is available

Use Bun 1.3.14. Keep the original export under the user-approved private archive
`/Users/sumanththota/Schrex/archive`, outside this checkout and synced folders.
The input must be a nonempty regular file owned by the executing user, with no
group/other permission bits and no hard links. Its immediate parent must also be
owner-only. The tool refuses resolved paths inside this repository. It does not
change permissions; verify and deliberately correct permissions before use if a
browser download is more permissive.

```sh
bun scripts/migration-inspect.mjs /Users/sumanththota/Schrex/archive/EXPORT_FILENAME
```

Replace the placeholder with the downloaded filename. Output contains only byte
size, SHA-256, a format candidate, and explicit blocked-restore/completeness flags.
Store the result privately alongside the archive; do not commit private manifests.
The CLI deliberately hides filesystem error details and never prints archive
contents or paths. It hashes incrementally and checks file size/timestamps before
and after inspection. Do not inspect while a download or writer is active.

Recognition is based on bytes, never extension: PostgreSQL custom magic, gzip,
ZIP, tar, or the conventional PostgreSQL plain dump header. Every result remains
unapproved for restore. A short/truncated archive can have valid magic. Unknown
or differently formatted SQL remains unknown. Container contents are not inspected.
No checksum proves completeness without an independent source manifest.

POSIX modes are a basic guard, not proof of macOS ACLs, disk encryption, backup
policy, sync exclusions, or a hardened host. Other repository locations cannot be
automatically discovered by this tool. The operator still owns those checks.

## What follows the fingerprint, before any import

1. Privately establish actual archive structure and integrity. For a genuine
   PostgreSQL custom archive, review a list generated by a compatible PostgreSQL
   `pg_restore --list` without a connection. For containers, review paths and
   extraction limits in a separate safe procedure before extraction. Do not run
   embedded SQL or trust filenames. No command is generated by this script.
2. Reconcile the complete schema/data inventory with live counts, all Auth state,
   required extension/platform state, and storage metadata. Definitions and queue
   contents may contain secrets. Keep detailed inventory private.
3. Produce a reviewed structural restore selection. Exclude only destination
   `cron.job_run_details` data, leaving source history and the original export
   untouched. Preserve business audit/log tables and queues. Do not use text-line
   deletion to remove SQL COPY payloads or assume a TOC filter prevents all jobs.
4. Inventory cron configuration rows, SQL function bodies, triggers, event triggers,
   extension configuration tables, subscriptions and outbound execution paths.
   Preserve necessary definitions privately and install an inert destination
   adaptation. An empty scheduler table alone does not prevent trigger delivery.
5. Establish a securely supplied restore connection whose project identity is
   independently verified as `acgqjjbrnkmeazswdnzp` (`hub-rehearsal`). Do not use the
   source `bitogpfplcquovpdjprk`, the synthetic local backend, or a guessed URL.
   Connection validation/allowlisting is not implemented by this offline script.
6. Confirm destination mail/hooks, subscriptions and scheduled workers are inert,
   disable public signup before real-data import, review extension compatibility,
   and measure post-exclusion data size against destination capacity.
7. Only then implement the archive-specific restore executor and test its handling
   of business rows, Auth identities/hashes, trigger effects and scheduler history
   on synthetic fixtures. Managed Auth/storage schema compatibility and encrypted
   Vault state require separate review; do not replay historical user seed SQL.

## Validation performed

```sh
bun run test --config scripts/migration-vitest.config.mjs
```

Ten synthetic Vitest cases pass: streaming checksum/content-free output, custom,
plain, gzip, ZIP and tar recognition, unknown format, empty-input refusal,
group-readable-file refusal, shared-parent refusal, and repository symlink refusal
(some checks share one case). No production rows, password hashes, or real files
are fixtures. The script-specific config leaves the application Vitest config and
dependency lockfile unchanged. Application/backend/Edge/browser behavior is not
changed; those suites are not evidence of this archive's eventual restorability.

Remaining gates: actual export access, format-specific integrity/completeness,
private full inventory, reviewed inert restore selection, secure destination
connection, destination compatibility/capacity/isolation, and independent restore
acceptance. Passing these synthetic tests proves none of those gates complete.
